# ADR 0028：候选刷新优先级与失败恢复

- 状态：P3 后体验优化已采用；修订 ADR 0026 的超时快照语义
- 日期：2026-08-03

## 背景

选择 `ni'hao'shi'jie` 中的“你好”后，TSF 能正确提交词语、删除 `ni'hao` 并将预览改为 `shi'jie`，但候选列表可能仍停在整句的视觉快照且无法交互。原因是后台传输对所有 Core 请求共用 100ms 上限，并在失败时直接丢弃结果，UI 的 `candidate_request_pending` 没有终态。完整词库实测中 `shi'jie` 首次进程间往返约为 77ms，100ms 在调度波动下缺少余量。部分提交后工作线程还会先发送非关键的学习反馈，进一步推迟剩余拼音的候选请求。

## 决策

1. 后台队列同时存在候选请求和提交学习反馈时，先处理最新候选请求。学习反馈继续保序且不丢失，但不能阻塞用户可见的刷新。
2. Core 候选传输保持异步，单次上限从 100ms 放宽到 500ms。这不会延迟正常响应，只为完整词库首次访问、进程调度和管道建立留出边界。非关键学习反馈仍保持 100ms 上限。
3. 候选传输失败、协议无效、request ID 不匹配或响应类型错误时，工作线程向 UI 投递与原 request、generation 和 page 对齐的失败终态。旧请求的失败仍按现有世代校验丢弃。
4. UI 接收当前请求的失败终态后，必须清除视觉快照的候选文本与消费范围、结束 pending，并显示“候选服务暂不可用”。不得继续显示与当前拼音不匹配的旧候选。

## 结果

“你好”部分提交后，`shi'jie` 的候选请求立即越过学习反馈并获得充足的异步传输余量。即使 Core 不可用或响应损坏，候选窗也会进入明确终态，不再永久保留旧整句候选并锁住交互。

## 边界

- 500ms 是传输失败上限，不是候选性能目标；引擎 Release 基准仍以低毫秒级为目标。
- 本次不在 TSF 内自动无限重试。新的字母、退格或分隔符会发起新世代请求；Escape 仍可取消当前组合。

## 回滚

恢复反馈优先队列和共用 100ms 传输上限，移除失败终态与错误文案。该回滚会重新引入请求失败后的永久 pending，不改变 Core 协议。
