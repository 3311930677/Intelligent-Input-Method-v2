# OwO 插件平台架构设计（多类型插件扩展）

- 日期：2026-08-03
- 状态：架构设计草案（面向 P4 及以后，不含实现）
- 目标读者：项目开发者
- 关联现状：P3C 插件框架已验收（ADR 0008~0021、`docs/security/plugin-baseline.md`）

---

## 0. 一句话目标

把 OwO 从「只能装一种零权限插件」升级为「能容纳**不同权限等级**插件的平台」，让 AI、语音输入、表情包等插件都能在**各自受控的安全边界内**运行。

核心不是「多写几个插件」，而是先建一套插件共用的地基：**权限分级 + 统一能力接口**。地基做好后，新增任何插件都只是「填空题」。

---

## 1. 现状：P3C 的插件框架能做什么、不能做什么

P3C 已经建成一个**极严格的零能力沙箱**（这是 OwO 最核心的安全资产，务必保护）：

| 维度 | 现状（v1） | 出处 |
|---|---|---|
| 运行形态 | `runtime=process`，入口固定 `bin/*.exe`，不进入 TSF/Core 地址空间 | ADR 0008/0012 |
| 网络 | **默认关闭，且由 AppContainer 令牌能力边界强制**（不是靠自报） | plugin-baseline / ADR 0012 |
| 文件 | 默认仅允许插件自己的数据目录 | plugin-baseline |
| 内存 | Job Object 单进程 **128 MiB** | ADR 0012 |
| 并发/时长 | 单插件 1 进程、1 在途调用、调用总期限 30 秒 | ADR 0015 |
| 权限模型 | **逐项声明、默认拒绝、升级需重新确认**；授权绑定精确版本+清单摘要+发布者证书 | ADR 0011 / plugin-baseline |
| 签名 | 必须受信 CMS 签名，完全离线失败封闭，无未签名开发模式 | ADR 0019/0021 |
| 外部调用 | P3C **不开放**外部调用入口，认证用户动作入口留到 P4 | ADR 0020 |

**关键结论**：现有框架**只能装「纯本地、不上网、算得快」的插件**。这套「逐项声明、默认拒绝」的权限模型是好底子——扩展方向不是推翻它，而是**在它之上增加更高的权限档位**。

---

## 2. 核心设计：插件权限分级（L1 / L2 / L3）

不同插件对权限的需求天差地别，必须分级管理。就像游乐场手环分颜色，插件在 manifest 里声明所需能力，OwO 按档位分配不同的运行环境与授权流程。

### 🟢 L1 —— 纯本地插件（沿用现有零能力沙箱）

- **能力**：只能本地计算，无网络、无设备、不访问其他进程。
- **典型插件**：表情包 / 颜文字、符号候选、编码转换、文本格式化。
- **运行环境**：现有零能力 AppContainer，**无需改造**。
- **权限档**：R0~R1（观察 / 可逆本地计算）。
- **落地成本**：低——与 OwO 自己规划的 P4「字符编码转换插件」同级。

### 🟡 L2 —— 受控网络插件（沙箱开「白名单窗户」）

- **能力**：在沙箱上开一扇**只能连指定域名**的窗户，其余仍禁止。
- **典型插件**：AI 润色 / 翻译（调云端 API）、在线词库。
- **运行环境**：AppContainer + **网络能力按域名白名单授权**。
- **与「方案 B 凿洞」的本质区别**：
  - L2 是 **OwO 官方、可控、按需授权**地开一扇只通指定地址的窗户，用户明确同意，OwO 审核域名。
  - 「方案 B」是插件**自己翻墙**连任意外部高权限进程 = 沙箱逃逸，不可控。
  - **两者形似神异，务必区分**。L2 安全可控，方案 B 不可取。
- **权限档**：R2~R3（数据出本机、外部影响），安装时必须显式确认目标域名。
- **落地成本**：中——需要给 AppContainer 增加受控网络能力，并扩展 manifest 网络声明与授权 UI。这是**对 ADR 0012「网络无条件禁用」边界的一次受控放宽**，需新开 ADR 记录。

### 🔴 L3 —— 系统/硬件能力插件（独立授权进程，不进沙箱）

- **能力**：麦克风、读其他窗口（UIA）、全局热键、屏幕捕获等。
- **典型插件**：语音输入、屏幕 OCR、跨应用助手（**灵犀本身就是一个 L3 大插件**）。
- **运行环境**：**不塞进沙箱**。做成**独立运行的授权程序**，OwO 通过「能力授权协议」与之通信。
- **授权模型**：直接复用灵犀技术路线文档里的 **Capability Grant + 风险分级 R0~R4**——用户明确点「同意让该插件使用麦克风」才授权，可设范围、时效、次数上限。
- **权限档**：R3~R4（硬件 / 系统级）。
- **落地成本**：高——需要一套独立进程的认证、授权、审计协议。但这正是**两个大创的天然结合点**。

### 分级速查表

| 档位 | 能力边界 | 典型插件 | 运行环境 | 改造量 |
|---|---|---|---|---|
| 🟢 L1 | 纯本地计算 | 表情包、符号、编码转换 | 现有零能力沙箱 | 无（已支持）|
| 🟡 L2 | 本地 + 域名白名单网络 | AI 润色/翻译、在线词库 | 沙箱 + 受控网络 | 中 |
| 🔴 L3 | 硬件 / 跨应用 / 系统级 | 语音输入、OCR、灵犀 | 独立授权进程 + IPC | 高 |

## 3. 平台地基：四块必须先建的公共设施

新增插件之前，要先补齐以下四块「所有插件共用」的地基。

### 3.1 权限声明 + 分级授权（最重要）

- 每个插件 `manifest.json` 声明所需能力，OwO 据此判定 L1/L2/L3 并走对应授权流程。
- 建议在现有 manifest 权限白名单基础上扩展分类，例如：
  - `local`（本地计算，L1）
  - `network.allow`（域名白名单数组，L2）
  - `microphone.capture` / `screen.capture` / `automation.uia` / `input.hotkey`（L3）
- 保留 P3C 的铁律：**逐项声明、默认拒绝、升级需重新确认、授权绑定精确版本+清单摘要+发布者证书**（ADR 0011）。
- L2/L3 安装时必须弹窗显示「该插件将访问：xxx」并要求用户明确确认。

### 3.2 统一能力接口（Capability API）

定义插件能向输入法请求的**标准动作集**，所有插件共用同一套接口（类似「充电口统一成 Type-C」）：

- `candidates.push`：向候选栏注入候选（表情包、AI 候选都用它）
- `selection.replace`：替换用户选中的文本（AI 润色用）
- `panel.show`：弹出插件自己的小面板（语音输入的录音条用）
- `text.commit`：直接上屏一段文本（语音识别结果用）

好处：OwO 不用为每个插件写专门对接代码；插件开发者照接口填空即可。接口须版本化（沿用 ADR 0015 的 `.v1` 版本化服务约定）。

### 3.3 插件管理界面（扩展现有设置中心）

- OwO 的 WinUI 设置中心已有插件管理雏形（列表 / 启停 / 卸载 / 恢复，ADR 0016/0021）。
- 需扩展：显示每个插件的**权限档位与已授权能力**，支持逐项撤销授权。

### 3.4 触发路由（插件何时被唤起）

定义「什么输入 → 唤起哪个插件」的规则：

| 插件 | 触发方式（示例）|
|---|---|
| 表情包 | 输入 `/xx` 前缀，或专用引导键 |
| AI 润色 | 选中文本 + 热键 |
| 语音输入 | 按住某键说话 |

路由规则本身应可配置，避免多个插件抢同一触发。

## 4. 落地路线（从易到难，不要一口吃成胖子）

```
第 1 步：表情包插件（🟢 L1）
   └─ 用现成零能力沙箱，跑通「安装→授权→出候选」完整链路，摸熟流程。
      不改地基。

第 2 步：建「权限分级 + 统一能力接口」地基（3.1 + 3.2）
   └─ 平台核心，也是本项目最能拿分的技术贡献。定死 L1/L2/L3 规矩与统一接口。

第 3 步：AI 插件（🟡 L2）
   └─ 给沙箱加「域名白名单网络」，新开 ADR 记录对 ADR 0012 的受控放宽。

第 4 步：语音输入插件（🔴 L3）
   └─ 做成独立授权程序，用 Capability Grant + R0~R4 授权协议对接。
      灵犀的技术路线文档已有整套设计，直接复用。
```

**分档带来的验收友好性**：每一档都能独立验收（L1 完全本地可测；L2 加网络白名单测试；L3 加设备/授权测试），符合 OwO 一贯的「分片验收」风格。

---

## 5. 安全底线（务必守住）

1. **默认拒绝、逐项授权、绑定版本** —— P3C 的核心原则在所有档位都不放松。
2. **L2 的网络是白名单，不是全开** —— 插件只能连声明并被批准的域名。
3. **L3 不进沙箱，但要更强授权** —— 权限越大，用户确认越明确，审计越完整。
4. **绝不做「方案 B 凿洞」** —— 不给沙箱内插件开「连任意外部高权限进程」的通道；需要系统能力就走 L3 独立授权进程的正门。
5. **每次放宽边界都要有 ADR** —— 尤其 L2 网络能力，是对 ADR 0012 的修改，必须留可审计决策记录。

---

## 6. 与灵犀（cross-app-assistant）的关系

- 灵犀不是「装进沙箱的插件」，而是一个典型的 **L3 独立授权程序**（它要网络、UIA、热键、桌宠，全是 L3 能力）。
- 因此两个大创的正确合体方式：**OwO 定义 L3 能力授权协议 → 灵犀作为第一个 L3 插件接入**。
- 灵犀中**纯本地、确定性**的那部分能力（如文本规整 Transformer），可另行抽出打成 🟢 L1 `.owopkg`，作为「灵犀也能产出合规插件」的信物（详见 `cross-app-assistant/docs/owopkg-plugin-feasibility.md`）。

---

## 7. 结论

- OwO 现有框架只支持 🟢 L1 插件；表情包可直接做。
- AI（🟡 L2）与语音（🔴 L3）需要**先把平台地基（权限分级 + 统一能力接口）建好**，再各自扩展网络白名单 / 独立授权进程。
- 这套「权限分级平台」既是新增插件的前提，也是本项目最有含金量的技术贡献；灵犀作为第一个 L3 插件，让两个大创自然合体。
