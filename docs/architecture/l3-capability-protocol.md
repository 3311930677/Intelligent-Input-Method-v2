# OwO L3 能力授权协议（草案）

- 日期：2026-08-03
- 状态：设计草案（占位，未实现）
- 关联：`docs/architecture/plugin-platform-design.md`（插件平台三档分级）

---

## 1. 为什么 L3 不走 owopkg 沙箱

L3 插件需要麦克风、屏幕捕获、UI 自动化、全局热键等**系统/硬件能力**。OwO 的 owopkg 插件运行在零能力 AppContainer 中，这些能力被令牌边界强制禁止（见 ADR 0012）。因此 L3 插件**不打包进 owopkg，也不进沙箱**，而是作为**独立进程模块**，由用户按需下载安装，经本协议向 OwO 申请能力授权后协作。

代表性 L3 模块：

- AI 文本处理（网络能力，严格说是 L2，但因其独立分发形态与 L3 一致，纳入同一协议）
- 语音识别输入（麦克风）
- 屏幕 OCR（屏幕捕获）
- 跨应用助手（UI 自动化 + 全局热键，例如 cross-app-assistant/灵犀）

---

## 2. 授权模型（复用 Capability Grant + 风险分级）

沿用桌面 Agent 的能力授权模型。授权对象是**具体能力**，不是"整个模块"。

```
CapabilityGrant {
    subject:      模块 ID + 精确版本 + 已验证发布者
    capability:   能力标识（如 microphone.capture / screen.capture / automation.uia / network.domain）
    scope:        作用范围（限定应用 / 限定域名 / 只读 / 仅本次会话）
    expires_at:   过期时间（可选）
    max_uses:     次数上限（可选）
    approval:     授权模式（每次确认 / 会话内 / 长期规则）
}
```

风险分级（模型只能提出，最终由规则引擎裁定，模块无权自行降级）：

| 等级 | 示例 | 默认处理 |
|---|---|---|
| R0 观察 | 读取活动应用名 | 自动允许 |
| R1 可逆本地 | 生成草稿、写临时文件 | 记录 |
| R2 影响用户数据 | 覆盖文件、应用 Diff | 预览后确认 |
| R3 外部影响 | 发送、发布、麦克风采集 | 每次明确确认 |
| R4 系统权限 | 系统设置、全局注入 | 系统认证 + 明确确认 |

## 3. 进程与信任

- L3 模块以**独立普通用户进程**运行，不继承 OwO 的令牌，不进入 TSF/Core 地址空间。
- OwO 与 L3 模块通过**本地 IPC**（命名管道 / 本地回环）通信，使用安装时协商的密钥双向认证。
- 模块的安装包仍应签名；OwO 校验发布者身份后，才允许其申请能力。
- 授权记录绑定模块 ID、精确版本、包摘要与发布者证书（与 owopkg 授权记录一致的绑定原则）。

## 4. 协议消息（占位契约）

版本化服务，消息以 `.v1` 结尾。核心消息：

- `capability.request.v1`：模块声明所需能力 + scope + 风险提示 → OwO 规则引擎裁定风险等级 → 弹用户确认。
- `capability.grant.v1`：OwO 返回受限授权令牌（含 scope、过期、次数）。
- `capability.revoke.v1`：用户或 OwO 主动撤销。
- `action.invoke.v1`：模块在已授权范围内请求 OwO 侧动作（如 `candidates.push`、`selection.replace`、`text.commit`、`panel.show`）。
- `action.receipt.v1`：动作回执（受影响对象、前后证据、可撤销令牌）。

约束（沿用现有插件调用面原则）：单模块并发上限、调用有界期限、负载上限、敏感调用需用户动作标记、审计不记录负载正文。

---

## 5. 与统一能力接口的关系

L3 模块通过 `action.invoke.v1` 使用的动作，与 owopkg L1 插件使用的**同一套 Capability API**（`candidates.push` / `selection.replace` / `panel.show` / `text.commit`）。区别只在：

- L1 插件：动作由沙箱内 PluginHost 中转，能力天然受限。
- L3 模块：动作由独立进程经能力授权协议申请，能力按 Grant 放行。

统一接口让"输入法能为插件做什么"只有一处定义，L1/L3 复用。
